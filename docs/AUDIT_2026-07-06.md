# Wiring Audit: iPhone bug fixes - song search + intro-to-song chain (2026-07-06)

Scope: two production bugs the coach reported on a real iPhone (Safari,
cellular) that desktop Chromium testing had not caught.

- BUG 1: song search failed with "Search failed. Check your connection and
  try again." Root cause: search used a single JSONP script tag to
  itunes.apple.com; on iOS/cellular that load failed (content blockers,
  carrier-IP rate limiting, or script.onerror).
- BUG 2: the PA-announcer intro played but the walk-up song did NOT follow.
  Root cause: in useAudioPlayer.play() the sync path found the intro blob in
  memCache but the (larger) song blob was not yet preloaded on cellular, so
  it called startIntroThenSong(intro, null, ...) which played the intro and
  stopped, never fetching the song.

Changed files: src/lib/songSearch.ts (rewritten), src/lib/useAudioPlayer.ts,
src/components/walkup/NowPlaying.tsx, src/pages/WalkUpPage.tsx.

## Fixes shipped

BUG 1 - three-layer search fallback in searchSongs:
1. plain fetch() to the iTunes Search API (endpoint reflects the request
   Origin in access-control-allow-origin, verified by curl for
   https://loulightning.com), 8s AbortController timeout.
2. JSONP script tag to the same Apple API (for CORS/fetch-blocked contexts).
3. JSONP to Deezer's search API (different provider + domain, survives Apple
   rate-limiting a shared carrier IP).
Both providers map to an identical SongResult shape; previewUrl always
present; both preview CDNs send access-control-allow-origin: * so
fetchPreviewBlob (now with a 15s AbortController timeout) is unchanged.

BUG 2 - fetch the song during intro playback:
startIntroThenSong now accepts song as Blob | (() => Promise<Blob>) | null;
play() hands off a fetcher (() => getAudio(id)) when the song is not in
memCache. The fetch starts synchronously (overlaps the intro) and the song is
swapped onto the same gesture-unlocked element at the intro's `ended`. A
buffering cue ("Loading song...") shows if the fetch is still in flight when
the intro ends.

## Round 1 (3 parallel agents: static, runtime/UX, copy/data)

Agent C (copy/data): ZERO FINDINGS. Error strings truthful under the new
fallback (only "Search failed" when ALL providers fail), mapper shape parity
confirmed, em-dash sweep zero, no private data.

Tier 2 (fixed):
1. songReady could reject before its .then was attached during the intro
   (unhandled rejection). FIX: made songReady non-rejecting (.catch(()=>undefined)).
2. fetchPreviewBlob had no timeout - a stalled clip download hung the import
   button. FIX: AbortController + 15s timeout.
3. Neither intro nor song audio element set onerror - an undecodable blob
   fired `error` not `ended`, stranding the overlay. FIX: onerror recovery on
   both startIntroThenSong and startSongOn.

Tier 3 (fixed):
- play() async-fallback Promise.all had no .catch (playingId could stick).
  FIX: added .catch.
- JSONP timeout left a permanent no-op on window[cbName]. FIX: self-deleting
  shim + 30s grace-period delete.
- No buffering cue during the intro-to-song gap. FIX: isBuffering flag ->
  "Loading song..." in NowPlaying.

## Round 2 (fresh agent on the fix batch)

Verified fixes 1-3, 5, 6, 7 correct. Double-fire analysis: onended and
onerror are mutually exclusive for a single playback EXCEPT the undecodable
intro case, where onerror fires AND play() rejects.

Tier 2 (fixed): fix #3's undecodable-intro recovery was undercut by the
pre-existing intro play().catch cleanup (they raced). FIX: made toSong
idempotent (advanced flag + nulls its own handlers) and routed the intro
play().catch through toSong so it advances to the song instead of tearing
down. Now exactly one advance runs.

## Round 3 verification (live browser, local prod build at 390x844)

- Search "Hulvey" (the exact term that failed on the phone): 6 results

  (no callback param) => 200. The primary fetch path works from a browser

- Play Elijah (has intro + song): exactly one <audio> element, intro played,

- Build: tsc -b + vite build clean. Em-dash sweep: zero.

## Verdict: CLEAN (audit clean, zero findings after fixes)
